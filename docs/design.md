# 设计文档

所有设计均基于本文档的精神

## 需求分析

为了有效利用空间，提供便捷的母盘+差异盘管理，在共享模式下同一份存储母盘通过多个差异盘提供给多个用户，通常情况下是共享一份游戏存储;
强制要求 **服务端、客户端必须轻量，UI简洁大气偏苹果风格（不做动效与透明效果）并且操作逻辑通顺**

## 服务设计

### 服务端 

#### 管理vhdx（不直接对用户暴露底层能力）
1. 创建vhdx，支持完整的功能参数（类型如差异盘、限制等完整的技术参数），支持从目录创建（含义是复制或剪切该目录的内容到盘里，在目录由内容时默认为用户填写表单中的数，以目录当前大小为准，向上取整到支持的最小限制单位）或创建空vhdx 
2. 查询vhdx 
3. 删除vhdx 
4. 复制vhdx（补充调研一些windows server 2025下的存储系统优化方案，能尽量省存储空间） ，只允许复制没有被iscsi共享出去并被用户连接的盘
5. 存储统计与读写监控

#### 管理iscsi（不直接对用户暴露底层能力）： 
1. 从vhdx创建iscsi，支持完整的iscsi原生鉴权能力，由服务端托管，建议用密钥的形式做
2. iscsi配置的基本管理
3. 查询、管理、监控iscsi连接

#### 存储库
1. 上述1~2点均不以原生能力的形式提供给用户，而是整合起来以存储库的概念给到用户
2. 支持从vhdx母盘创建vhdx差异盘并分配给用户，分配时平台自动管理密钥等（也支持无鉴权或IP鉴权），客户端在挂载时查询对应的参数并完成挂载，注意一般只给挂载差异盘，母盘在只有没有任何差异盘或本身没有被挂载的情况下可以被临时挂载（临时挂载状态需要落盘，可以引入一个“维护”状态，进入维护状态需要支持清理差异盘），临时挂载完成断开后会移除母盘上的iscsi共享，为了避免各种异常情况，要能完整管理这个临时的共享（假如我在挂载这个临时的iscsi后服务器挂了，我重启服务器还能够去管理这个临时的共享，可以取消掉）只有没有共享的母盘才可以生成差异盘，作为正常使用（该功能为共享存储库模式与3.3中的【独享】存储库能力互斥）
3. 独享模式，只提供vhdx+iscsi，以及基本的管理能力
4. 存储库的基本管理：创建，复制，删除，查询，分配（只有共享模式可以分配给多个用户），修改一些基本信息
5. 存储库的状态查询以及基本配额监控（如果能做到读写监控最好，如果不行就做基本的资源容量管理）
6. 公共存储支持可管理列表，支持枚举用户名，以输入框+搜索选定的形式交互，添加到可管理列表中，持有权限的用户即为可管理，这个只有创建者可以设置
7. 一些额外的为客户端准备的存储和配置能力（存储到存储库的逻辑记录字段中，而非存储本身）
8. 支持分组管理，仅作为标签归类能力，交互为：用户编辑后在客户端可以分组展示，这个能力对服务端无用，存储逻辑见第7点

#### 平台后端抽象（Windows / Linux 并列）

「虚拟磁盘 + iSCSI」这层按平台抽象为**可替换后端**，上层（存储库 / 分配 / 租约 / 对账 / 上传）不感知平台差异：

| 能力 | Windows 后端 | Linux 后端 |
| --- | --- | --- |
| 虚拟磁盘 | VHDX（VirtDisk API） | LVM thin 逻辑卷（thin provisioning） |
| 差异盘 | VHDX 差异盘 | LVM **thin 快照**（不占额外容量） |
| 只读共享 | iSCSI 只读映射 | LIO 的 **per-ACL** `write_protect` |
| iSCSI 服务 | Windows iSCSI Target Server（PowerShell） | **LIO**（configfs 直控，零外部依赖） |
| 会话枚举 / 强制踢下线 | ❌ 均不支持（只能靠客户端心跳） | ✅ LIO 可枚举会话、可强制登出 |
| 缓存加速 | 依赖底层卷能力 | LVM **dm-cache**（SSD 加速 HDD） |
| 引用标识（ref） | VHDX 绝对路径 | `/dev/mapper/<vg>-<lv>` |

要点：
1. 平台由**构建产物**决定（同一份代码分平台编译），`platform.kind` 配置仅用于一致性校验，写错**直接拒绝启动**，不做静默回退。
2. 差异盘在 Linux 上是 thin 快照，**天然省空间**；因此 Windows 侧"复制不省空间"的短板在 Linux 侧不存在。
3. Linux 侧有会话枚举与强踢能力，但**为保持上层一致**，客户端心跳仍是"在线状态"的权威来源，LIO 会话只作为交叉校验与纠偏手段。

#### LVM 存储池与缓存设备选择（Linux）

Linux 侧所有虚拟磁盘落在**一个 LVM thin pool** 上：

1. 池由管理端「初始化存储池」**一次性**创建：勾选数据盘组成卷组（VG），在其上建 thin pool（块大小 / 元数据大小 / 水位可配）。
2. 可**可选地勾选 SSD 作为 dm-cache**：缓存本体由 **LVM 原生 dm-cache** 承担，本系统**不自行实现缓存层**，只负责"把选定的块设备交给 LVM"。
3. 缓存设备从服务端枚举出的块设备列表中选择；**系统盘**（承载根 / 引导 / swap）、已挂载或有文件系统、已属其它卷组、已有子分区的设备一律**置灰并给出原因**——判定真源在**服务端**，前端不重复实现规则。
4. 缓存设备**不进配置文件**：由 LVM 自身持久持有，配置文件只描述 VG / thin pool 位置与建池参数。
5. 初始化**幂等**：已存在的 VG / thin pool / 缓存一律跳过，**绝不覆盖既有数据**；池的扩容仍在服务端命令行完成，管理页只展示现状。

#### 「存储」在 Linux 上也是受管 thin LV

Windows 上「存储」是 NTFS 卷上的一个普通目录；**Linux 上它升级为受管的 thin LV**——
`storages.path` 是**底层卷的挂载点**，不是宿主机上的任意目录：

1. 创建存储时服务端自动完成 `lvcreate → mkfs（ext4 默认 / xfs）→ mount`，
   挂载点默认 `/var/lib/vault/storages/<名称>-<短 ID>`（高级可自定义）。
2. 存储卷与磁盘卷是**同一 thin pool 下的两个平行 LV**（LV 不能嵌套）：
   存储 LV 只承担「上传暂存 + 回收站 + 孤儿扫描目录 + 容量配额」，**不参与磁盘布局**。
3. 支持在线 **挂载 / 卸载 / 扩容**（仅 super_admin）；扩容只增不减，`lvextend` 后自动扩展文件系统。
4. **挂载持久化由服务端负责**：启动时 + 每 5 分钟对账都会幂等重挂，不写 `/etc/fstab`、
   不生成 systemd unit。挂载后必须核对 `/proc/self/mountinfo`，**fail-closed**：
   未确认挂载的存储会被剔除出落盘集合——否则写入会静默落到宿主根文件系统上。
5. 保留「登记已有目录 / 已有 LV」作为高级逃生入口；登记进来的卷**只挂载、不格式化、
   删除存储时也绝不 `lvremove`**。
6. 因此 Linux 上 `storage.whitelist_roots` **不再作为存储种子**（会种出一个绕过 thin pool 的目录存储），
   仅作为 `GET /v1/fs/*` 与建库 `source_dir` 的默认浏览白名单来源。

> 与磁盘布局的关系：虚拟磁盘的**物理位置仍由配置的 VG 决定**，存储 LV 只决定"暂存/回收站/扫描目录放哪"，
> 两者是不同的 LV，互不嵌套。

#### 本地用户
1. 支持证书鉴权，本地安装证书，限制使用的IP地址
2. 作为分配资源的载体
3. 支持本地超级管理员，账号**存放在数据库中**（由初始化流程创建），保存 hash 过的密码（argon2id），可关闭，仅超级管理员可以创建用户，创建的用户存在数据库中，注意不要存明文密码
   - 配置文件只保留**开关**（`security.super_admin_enabled`），用于启用/停用该角色登录（收紧权限或锁定恢复），不再在配置里存账号与口令哈希
4. 一些额外的为客户端准备的存储和配置能力

#### 限制
1. 限制允许创建的服务端目录路径，白名单模式，配置中存储，在白名单目录内支持用户列举目录并选择

#### 管理页
1. **管理页与客户端合并为同一个应用**：客户端安装后配置服务端地址即可使用全部能力（含管理功能）。
   服务端因此**只提供 REST API，不再挂载任何 Web 静态资源**（无浏览器访问入口）。
2. 管理模块可见性由角色决定，仅超级管理员可见；普通用户只看到与自己相关的页面。
3. 管理页与用户页**组件级复用同一套 UI**（同一份 UI 真源、同一套设计 token、同一套语言包、同一套 API 客户端）。

#### 初始化
1. 提供一个**类似路由器初始化**的引导向导（做在客户端里），在「没有超级管理员且没有任何数据」时进入，
   用于确认系统从未被使用过并引导用户完成初始设置。
2. 向导至少包含：欢迎说明、管理员账号设置（含口令强度校验）、服务端显示名、确认、完成；完成后直接进入控制台。
3. 初始化**只允许成功一次**且必须并发安全；服务端需提供配置开关与可选的时间窗口来收紧开放条件。
4. 服务端启动时如检测到尚未初始化，应在日志中给出明确提示。

### 客户端

#### 存储库
1. 基本的存储创库建、管理、挂载能力
2. 支持存储库从非服务器目录创建（可中断的分块传输能力，先从客户端传到服务端，服务端再去创建）
3. 配置是否自动挂载以及挂载形态（支持挂载为盘符或在某个本地目录下），用户配置同步到服务端（见服务端-本地用户-4）
4. 支持挂载后执行脚本，在服务端存储这个脚本（见服务端-存储库-7）
5. 本地设置挂载的路径（挂载到目录模式下生效）以及一些基本的行为设置

#### 用户配置
1. 未配置服务端时提供一个输入并保存服务端的能力，支持客户端本地去切换
2. 首次登录时无用户，进入用户配置页，尝试以现有的证书+网卡去枚举尝试登录，尽量自动化

#### 模块划分
1. 本地操作模块，真正的客户端本地部分，涵盖存储库、用户配置、自动更新等
2. 管理模块，管理页的UI和逻辑，支持用户在本地管理

#### 自动更新
1. 客户端启动时自动检查服务端更新并且完成下载和重启以及更新，不影响挂载行为
2. 支持在 客户端-设置-更新 中手动检查更新并完成自动更新
`
#### i18n
1. 支持主流多语言，包括中文、英文、日文、韩文，在工程管理上需要可控以挂载kv格式语言包的形式去做，方便后续扩展
2. 支持在客户端中、管理页切换语言

#### 可操作性
1. windows下要有系统托盘图标，支持在后台运行与打开
2. windows下支持添加一个快捷的驱动器，打开到挂载的路径

#### 心跳
1. 因为Windows iSCSI Target Server 既没有会话枚举 API，也没有按会话强制登出 API，所以需要客户端自己实现心跳机制，定时向服务端发送心跳包，告知连接状态，服务端收到心跳包后记录提供枚举能力以及告知客户端断开连接，从而实现iscsi在客户端的断开连接能力

#### 多服务端
1. 支持客户端配置多个服务端，这里做个版本限制，只有版本对应的情况下才会加载对应服务端的资源
2. 获取客户端自动更新资源时只以第一个设置的服务器为准


## 技术选型
1. 服务端：golang + cgo（必要时）——**实际零处需要，统一 `CGO_ENABLED=0`**；Windows / Linux 双平台分构建编译
2. 客户端：golang + typescript + react + antd + electron（尽量打包成单一执行文件）
3. 管理页：typescript + react + antd
4. 数据库：mysql/sqlite
