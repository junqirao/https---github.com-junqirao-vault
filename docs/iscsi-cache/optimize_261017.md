## 0. 一句话结论

- **索引侧**：`readCachedL1` 每个块要 **3 次加解锁 + 3 次 map 查找 + 2 次 64 位取模**，
  外加 2 次「循环拼扇区掩码」。1MiB 命中读（16 块）= 48 次加解锁；最大长度读（256 块）= 768 次。
  其中**大部分 `touch` 的锁是空操作**，而 `Stats()` 是**两次全分片遍历、约 512 次加解锁**。
- **管理侧**：`sample` 每 5 秒把每个库的**全部分片**扫一遍，且**整轮持 `historyMu`** ——
  库多时是一次周期性尖峰，还会把 `GET /agent/cache/history` 挡在后面。

**但先说定位，否则会优化错地方**：

> `optimize_261016.md` §1.2 的实测 profile 里 `runtime.lock2` 只占 0.04s / 6.30s 样本（**0.6%**），
> `WSASend` 占 **61%**。**索引内部的锁不是当前的热点。**

所以本文的定位是「顺手收掉的固定开销」，拿 CPU 大头的仍是那份文档的
**O3（先建口径）→ O4（tee 免拷贝）→ O5（命中两次拷贝合一）→ O7（4K 块大小）**；
本文与它们**不重复**，边界见 §4。

## 1. 几何与量级

`cache.go:26-30`：`BlockSize = 64KiB`、`SectorSize = 4KiB`、`Shards = 256`。
下表的常数要按这个乘：

| 单条读命令 | 块数 | 加解锁 | map 查找 | 64 位取模 | 掩码循环 |
|---|---|---|---|---|---|
| 4KiB | 1 | 3 | 3 | 2 | 2 |
| 1MiB | 16 | 48 | 48 | 32 | 32 |
| 最大长度读（16MiB） | 256 | 768 | 768 | 512 | 512 |

> 块数 = 长度 ÷ 64KiB（向上取整）；掩码循环每次 ≤ `BlockSize/SectorSize` = 16 次迭代。
> 三种长度都指**单条命令**的长度，不是负载的 IO 大小分布。

### 2.2 详解

#### I1. 命中路径两遍遍历 → 单遍（收益最大，需与 O5 同批）

**现状**（`readCachedL1`，`cache.go:668-703`）

- 第一遍（`:671-684`）**只验证不拷贝**：`c.shard(blk).lookup(blk)`（`:679`）= 锁 1 + map 查找 1；
- 第二遍（`:685-700`）`sh.lookup(blk)`（`:693`）= 锁 2 + map 查找 2，再 `sh.touch(e)`（`:697`）= 锁 3；
- 每块 **3 次加解锁 + 3 次 map 查找 + 2 次取模**；`copyIfValid` 内部还会**再算一次** `rangeValid`
  （`:1435-1443`），这就是 §1 表里「掩码循环 ×2」的来源。

**为什么是两遍**：`:651-654` 的注释写明 —— 先验证整段再拷贝，这样「部分命中按整段 miss 上报，
且不为那些本来有效的块虚增 L1 计数器」。

**改法**：合并成单遍，逐块在同一临界区内完成「校验 + 拷贝 + 提升」；
`L1Hits` / `RequestHits` **移出循环、全成功时按块数一次累加**，语义与现在等价。

**落地前必须确认的一条**：失败时 `dst` 已被写过一部分（现在不会）。调用方在返回 `false` 时
是否使用 `dst` 的既有内容？`session.go` 的 `handleRead` 是「取池缓冲 → `ReadCachedBoth` →
不命中就整段转发」，看起来安全 —— 但**这正是 O5 要改的代码**，两件事必须一起设计、一起验证，
不要单独动其中一件。

**收益**：每块 3 → 1~2 次加解锁（相邻块落在不同分片，除非做 I4，否则无法合并成一把锁）。
1MiB 命中读：48 → 16~32 次。**必须 bench**，别按直觉下结论。

#### I2. `touch` 的锁在常见路径上是空操作（先做）

**现状**（`cache.go:1517-1528`）：`s.mu.Lock()` 写在 `if e.q == queueOld && ...` **之外**。
命中项绝大多数时间待在 `newQ`/`midQ`，拿锁进去什么都没改就解锁 —— **每块白付一次 mutex 往返**。

**改法**：只在可能提升时才进临界区。`e.q` 是 `uint8`、由所属分片锁保护（`:1419`），
无锁读它是「可能读到旧值」的启发式判断：最坏结果是**漏掉一次提升机会**（下次命中还会再判），
不影响正确性 —— S3-FIFO 本身就是启发式。

**收益**：每块省 1 次加解锁。**零语义变更**，跟着 I1 一起做或单独做都可以。

#### I3. `Stats()` 是两次全分片遍历（先做）

**现状**（`cache.go:371-375`）：

```go
s.L1UsedBytes, s.L1LimitBytes = c.Usage()        // :373  遍历 256 分片，每片 liveBlocks() 加锁
s.L1ResidentBytes = c.ResidentBytes()            // :374  再遍历一遍，每片 residentBytes() 再上锁
```

`Usage()`（`:421-425`）→ 每分片 `liveBlocks()`（`:1508-1513`，一次加解锁）；
`ResidentBytes()`（`:399-405`）→ 每分片 `residentBytes()`（`:407-415`，再一次加解锁）。
合起来 **256 × 2 = 512 次加解锁/次调用**，而它被：

- `agent` 的 `sample` 每 5 秒对**每个库**调一次（`cacheproxy.go:262` → `Stats`）；
- `GET /agent/cache` 的 `Status()` 对每个库调一次（`cacheproxy.go:808`）；
- `dropAll` / `dropCache` 为了写一条日志调一次（`session.go:672`、`target.go:292`）。

> 注：第二遍 `ResidentBytes()` 就是内存治理 M4 新加的估算。它当时是"能查到就行"，
> 现在要按本文档的定位收掉重复遍历。

**改法（二选一）**

1. **合并遍历**：一次遍历分片，同时取 `len(blocks)` 与队列容量（一把锁内取两个数），512 → 256；
2. **原子计数**（更好）：在每个分片维护 `liveBlocks`、`residentBytes` 的原子计数，在
   「插入 / 驱逐 / 出队 / 清槽位」处同步增减，`Usage()`/`ResidentBytes()` 变成一次全表原子读，
   **零加锁**。注意 M1 改过的三个出队点与 `removeLocked` 都要同步维护，否则账会漂。

**收益**：把 5 秒一次的周期性尖峰（库数 × 512 次加解锁）与状态接口的延迟一起抹掉。
`Stats()` 的调用频率见 §3 的 G1/G2/G4。

#### I4. 分片改**区间**划分（结构性，需实测取舍）

**现状**（`cache.go:1380`）：

```go
func (c *Cache) shard(blk uint64) *shard { return c.shards[blk%uint64(len(c.shards))] }
```

轮转分配 ⇒ **连续的 16 个块落在 16 个不同分片**，一条 1MiB 命中读至少要 16 把锁（I1 之后仍是 16 把）。

**改法**：改成区间划分 `blk / blocksPerShard` ⇒ 连续块落**同一分片**，I1 之后**一把锁就能服务整段**。
`blocksPerShard = (总容量/blockSize)/Shards`，保持每片容量不变。

**代价（必须实测，不能只算账）**：访问偏斜从「按 LBA 均匀打散」变成「按区间集中」——
热点区间会挤进同一个分片的队列，而分片容量与队列配额是按分片独立算的
（`capacity` / `newQuota` / `midQuota` / `high` / `low`，`cache.go:1472-1476`、`1480-1496`）。
所以**热区间的命中率与驱逐行为会变**，要拿「CPU 每 IO + 命中率」两项一起 A/B，
尤其是有扫描检测、顺序流与随机混跑的负载。

**折中方案（更便宜）**：把 `Shards` 从 256 调到 **64 或 32**。I1/I5 落地后每块的锁本就少了，
256 分片的并行度未必还必要，而分片变少意味着连续读碰到的分片更少、map 更小、`Stats()` 遍历更短。
这条只调参、不改语义；但 agent 目前不显式配置几何（只传 L1/L2 字节数与路径），需要加配置项。

#### I5. `shard()` 用 64 位取模（先做）

分片数是 2 的幂（`DefaultShards = 256`，`cache.go:29`），却用 `%`：每块 2 次
（`:679`、`:692`，都经 `:1380`）。改成 `& (n-1)` 即可，每块省 2 次 64 位除法。
**零语义变更**，但要注意配置允许 `Shards` 非 2 的幂（`:111-113`），保留取模兜底分支。

#### I6. `installValidated` 在分片锁内做至多 64KiB 拷贝（p99 项）

**现状**（`cache.go:1166-1215`）：`sh.mu.Lock()`（`:1175`）之后的临界区里依次做了
epoch 校验（`:1176`）、新 entry 的 `make([]byte, c.blockSize)`（`:1182`）、
**逐扇区 `copy`**（`:1196`）、`maintainLocked()`（`:1186`，可能驱逐并 `delete`）。
而读路径要的**正是这把锁**（`lookup`/`touch`）—— 每次 miss 填充都会把该分片的命中读
挡住一个 ≥64KiB memcpy 的时间。

**改法**：新 entry 在**锁外**分配并填好（此时它还没进 map，没有并发读者），
锁内只做「epoch 校验 + 挂接 map/队列 + 驱逐」；epoch 已变则丢弃。

**必须保住的约束（正确性相关）**

1. **先 copy 再置 `valid` 位**，且保留「已 valid 的扇区跳过」的语义（`:1189-1199`）——
   它保证并发读者看到的字节与它读到的 `valid` 一致；
2. **`fence.enqueue()` 必须留在临界区内**：`:1203-1205` 的注释写明，L2 序号与 epoch 校验
   在同一临界区里分配，失效才保证看得到每个携带写前数据的填充。顺序不能挪；
3. `entry.data` 现在**分配后永不复用**（`:1412-1413` 的注释，也是"读者持有的指针在淘汰后仍有效"
   这条保证的基础）。**如果将来把块缓冲池化，I6 必须重新设计**，否则写到已回收内存。

**收益**：分片锁持有时间显著缩短（对读 p99 有意义，对 CPU 总量意义有限）。**需 bench**。

#### I7. 队列摘除是线性扫描（O7 的前置）

**现状**：`removeFromQueueLocked`（`cache.go:1545`）用 `for i, x := range *q` 找元素（`:1553`）
再手写左移。每次把 entry 从 `oldQ` 提升回 `midQ`（`touch`，`:1523`）以及每次驱逐都要扫一遍队列。

**改法**：`entry` 加一个队列下标字段，O(1) 交换删除并维护「被换过去那个 entry」的下标。
注意：`maintainLocked`（`:1580`）的出队点、`removeLocked`（`:1540`）、`drop`（`:1530`）都要同步维护。

**两个连带影响**

- `entry` 头会从 48B 变成 56B（见 I8），**M4 的 `ResidentBytes` 估算常量要同步**，
  否则估算失真、`TestEntryHeaderBytes` 的守卫值也要一起改；
- 这条是 **O7（把块大小改小）的前置**：块变小 ⇒ 索引条目 ×16、队列 ×16 变长，
  线性扫描的成本会直接放大。

#### I8. 伪共享（需实测）

结构体布局（`cache.go:1414-1420`、`1456-1477`）：

- `entry`（48B）：`blk uint64`(8) + `data []byte`(24) + `valid atomic.Uint32`(4) + `freq atomic.Uint32`(4)
  + `q uint8`(1) = 41 → 48（7B 填充）。**`valid` 与 `freq` 相邻**，而 `freq` 每次命中都写；
- `shard`：`c`(8) + `mu sync.Mutex`(8) + `epoch atomic.Uint64`(8) + `blocks` map 头(8)
  **全落在第一个 64B 缓存行内**。`epoch` 的注释（`:1460-1464`）说「用普通原子读就不把分片锁
  放上读路径」，但它和锁本身同行 —— 两个读者各自 `epoch.Load()` 也会让该行来回失效。

**改法**：`epoch` 挪到独立缓存行（padding），或把只读字段与热写字段分行；`entry` 同理。
**收益只能靠实测**（看 `lock2` 占比或 per-shard 计数），读代码定不了，不要先动手。

#### I9. 扇区掩码用循环拼（先做）

**现状**（`cache.go:1425-1431`）：

```go
func (e *entry) rangeValid(s0, s1 int) bool {
	mask := uint32(0)
	for i := s0; i <= s1; i++ { mask |= 1 << uint(i) }   // ≤16 次迭代
	return e.valid.Load()&mask == mask
}
```

每块被调 **2 次**（`:680` 一遍、`:1438` `copyIfValid` 内再一遍）⇒ 整块读要跑 32 次迭代，
只为算一个**只取决于 (s0, s1) 的常量掩码**。

**改法**：预计算一张 `[33]uint32` 表（下标 = 扇区数，值 = 低 n 位全 1），
`mask := table[s1-s0+1] << uint(s0)`。一次移位代替整个循环。
> 不要写成 `(1<<(s1+1)) - (1<<s0)`：`s1` 最大 31 时 `1<<32` 在 `uint32` 上溢出为 0，
> 会静默算出错误掩码。查表形式没有这个坑。

**收益**：每块省 2 个 ≤16 次的循环。**零语义变更**。

## 3. 管理侧：`internal/agent/cacheproxy.go`

### G1. `sample` 整轮持 `historyMu`，且逐库穿透到全部分片

**现状**（`cacheproxy.go:253-292`）

```go
m.historyMu.Lock()                       // :258  整轮持有，defer Unlock
for _, key := range p.Keys() {           // :261  门户内每个库
    stats, ok := p.Stats(key)            // :262  → c.Stats() → 全部分片遍历（见 I3）
    ...
    m.history[key] = append/trim         // :281-285
}
```

每 5 秒（`cacheHistoryInterval = 5 * time.Second`，`:136`）一次，成本 ≈ **库数 × 512 次加解锁**
（I3 落地前），期间 `History()`（`:295-305`，`GET /agent/cache/history`）阻塞在同一把锁上。
库少时无所谓，**库多时这是一条周期性尖峰**。

**改法（两件事分开做）**

1. **依赖 I3**：`Stats()` 变便宜之后，这条的成本自己就掉下来了 —— 先做 I3，再评估要不要动这里；
2. **缩短持锁范围**：先在**短临界区**里取出 key 列表，再在锁外逐库采样、最后短锁内写回
   （注意 `alive` 清理逻辑要与采样结果合并，别把删除时机提前）。

**风险**：低。只是把"计算"移出临界区，不改变采样点的值与节奏。

### G2. `Status()` 每个 key 两次独立查表

**现状**（`cacheproxy.go:807-812`）：`p.Stats(key)`（`:808`，且内部遍历全部分片）后再
`p.TargetIQN(key)`（`:812`）—— 同一个 key 查两遍门户表、加两次锁。

**改法**：合成一次快照查询（让门户提供「一次拿到 stats + IQN」的接口），或至少在同一临界区内取两者。
**收益**：`GET /agent/cache` 的每库成本减半（叠加 I3 后更明显）。

### G3. 配额在 `EnsureTarget` 里无条件重算（低优先）

**现状**：`quotaFor(req)` 在 `cacheproxy.go:409` 调用，**在** `p.Add(...)`（`:432`）之前，
因此「库已存在、只是幂等重复挂载」这条路径上也会算一遍：`quotaFor`（`:484-508`）会
`cachePoolRepos` + 逐库 `knownRepoSize` + `splitCacheBudget`（`:503`、`:505` **各算一次**，
每次返回一张 map 再取一个 key）。

**评估**：**只在挂载时发生，不是热路径**，收益有限。价值主要在「幂等复用真的不做事」的整洁性，
以及 `splitCacheBudget` 被调两次可合并为一次。**不建议现在动**，列出备查。

> 另：每命令两次 `t.mu`（`lunBlockSize()` + `getCache()`）是同一类问题的**热路径版本**，
> 已记在 `optimize_261016.md` 的 O6 表里，本文不重复。

## 5. 批次与实施顺序

### 第一批：只删操作、零语义变更（不需要基线就能确定净收益，可合成一个 PR）

| 编号 | 内容 | 每块/每次省下 |
|---|---|---|
| I2 | `touch` 仅在可能提升时加锁 | 每块 1 次加解锁 |
| I5 | `shard()` 取模 → 掩码 | 每块 2 次 64 位除法 |
| I9 | 扇区掩码查表 | 每块 2 个 ≤16 次循环 |
| I3 | `Stats()` 合并遍历（或原子计数） | 每次约 256~512 次加解锁 |
| G2 | `Status()` 每 key 一次查表 | `GET /agent/cache` 每库减半 |

**诚实说明量级**：单条 4KiB 命中读大约省下 2 次加解锁 + 2 次除法 + 2 个小循环 ——
**这不是 CPU 大头**（见 §0 的定位）。这一批的价值在于：高 IOPS 下不再白付、
把 5 秒一次的周期性尖峰抹掉、以及**为 I1 铺路**。所有改动都不碰接口、不碰数据所有权，
所以不需要先有 profile 也能确定是净收益。

### 第二批：需 bench 才能定值（先按 §6(a) 建口径）

| 编号 | 内容 | 前置 |
|---|---|---|
| I1 | 命中路径两遍遍历 → 单遍 | **与 O5 同批**；需先确认 `dst` 被部分写脏的安全性 |
| I6 | 填充拷贝移出分片锁 | 需保持 `fence.enqueue()` 在临界区内 |
| I7 | 队列摘除 O(1) | 同步 M4 的 `ResidentBytes` 常量与守卫测试 |

### 第三批：结构 / 调参，需实测取舍

| 编号 | 内容 | 取舍点 |
|---|---|---|
| I4 | 分片改区间划分，或 `Shards` 256 → 64/32 | 热区间集中后命中率与驱逐行为会变，要 A/B |
| I8 | 伪共享 padding | 收益只能实测，先别动手 |
| G1 | `sample` 缩短持锁范围 | 依赖 I3 先落地 |

### 不建议现在动

- **G3**（配额重复计算）：只在挂载时发生，不是热路径，收益有限。

## 6. 验收口径

把 `optimize_261016.md` 的 O3 拆成两半，其中**一半本文档自己就能用**：

**(a) `internal/iscsicache/cache` 包内 micro-bench**（约 20 分钟可写，不需要 iSCSI 栈、不需要真后端）

- `BenchmarkReadCachedL1`：4KiB / 64KiB / 1MiB **命中**读；
- `BenchmarkReadCachedBoth`：L2 命中（含回填提升）；
- `BenchmarkStats`：单次 `Stats()`；
- `BenchmarkInstall`：miss 填充。
- 指标：`ns/op`、`allocs/op`；配 `-cpuprofile` 看 `lock2` 占比。

这是 **I1 / I2 / I3 / I5 / I9** 的直接验收口径，也是「锁到底是不是热点」的白盒答案。

**(b) `internal/iscsiproxy` 端到端 bench + pprof 开关**：仍是 O3 里重的那一半
（需要内存 LUN 后端构造），用于验证 O4/O5 与本文第二批、第三批的端到端收益。

**另建议加一个白盒计数断言**：在 `readCachedL1` 临时埋 `atomic` 计数（加解锁次数、掩码循环次数），
用测试断言「1MiB 命中读 = 3 × 块数 次加解锁」这个**当前上界**，落地后收紧到 1~2 × 块数 ——
防止后人悄悄把锁加回去。风格与内存治理 M1 那个反向验证过的测试一致。
