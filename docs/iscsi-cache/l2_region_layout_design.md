# L2 区域归位布局设计（把随机命中变成顺序读）

> 目标：让 L2 命中在**文件层面**变成顺序读。
> 本文档只做设计，未改动任何源码。行号对应 2026-10-17 的工作区状态。

## 0. 前提与结论

**负载前提（本文档成立的全部基础）**：实际使用中的随机读，其**访问路径是相对固定的**，
且这些路径**能被块粒度覆盖** —— 即热集是 LBA 空间里一组稳定的、块级的区域，
不是"任意时刻任意 4KiB"。

在这个前提下，结论是：

> **L2 的物理位置不应该由"到达顺序"决定，而应该由 LBA 决定。**
> 只要把「LBA 相邻 ⇒ 物理相邻」做成布局的硬不变量，
> 那么"路径固定的随机读"在磁盘上就自动变成"一组固定的、连续的 extent"，
> 一次 `pread` 就能整段读走 —— 不需要任何预测、不需要重排、不依赖访问模式检测。

本文档给出的方案是 **区域归位（region-homed layout）**：

| | 现状 | 本方案 |
|---|---|---|
| 物理位置由什么决定 | **到达顺序**（环形 FIFO 分配） | **LBA**（区域归位，块内直映射） |
| 同一区域相邻块是否物理相邻 | 否（被打散到任意槽位） | **是**（硬不变量） |
| 1MiB 命中读的 I/O 次数 | **16**（各 64KiB，互不相关） | **1~2**（≤ maxIO 的连续读） |
| 每块元数据开销 | 20B 索引 + **4096B stamp** = 5.9% | ≈0.3B 索引 + 0.39% stamp |

代价是**区域内的容量浪费**（区域只热一部分时，home 内空槽不能用），
这是本方案唯一的实质代价，第 2.7 节给出量化与旋钮。

## 1. 现状：为什么今天必然是随机 IO

四个事实，缺一不可地导致"命中即随机"：

| # | 事实 | 证据 | 后果 |
|---|---|---|---|
| 1 | 槽位**环形 FIFO 分配** | `l2.go:904-906` (`num := f.next; f.next = (f.next+1)%f.slotCount`)，`l2.go:200-201` 注释 | **物理位置 = 到达顺序**，与 LBA 无关 |
| 2 | 填充是**多 worker 异步**的 | `DefaultFillWorkers`；每次回填 `go c.writeL2(...)`（`optimize_261016.md` O8） | 到达顺序**连"顺序读的顺序"都不是** ⇒ 冷启动刚预热完就已经是乱的 |
| 3 | 读路径**逐块**调用 | `cache.go:780` 每块一次 `c.l2.ReadSectors`；`ReadSectors` 一次 `ReadAt`（`l2.go:646`） | 1MiB 命中读 = **16 次互不相关的 64KiB IO** |
| 4 | `FILE_FLAG_NO_BUFFERING` + 4 个共享句柄 | `store_windows.go:135`、`:21-31`、`:203-207` | **OS 预读/页缓存全关**，没有任何机制会合并相邻访问；设备并发深度上限 ≈ 4 |

事实 4 尤其关键：换了普通带缓存的文件 IO，NTFS + 缓存管理器会替你合并一部分相邻读；
而 `NO_BUFFERING` 把这条路彻底堵死了 —— **顺序与随机的差别，完全由我们的布局决定**。

**还有一个必须一起解决的硬约束**：

```
l2.go:303                 openStore(cfg.Path, fileSize, maxInt(slotSize, SuperBlockSize))
store_windows.go:200-202  if len(p) > len(sh.scratch.buf) { return 错误 }
```

`maxIO` 传的是 `slotSize` = **64KiB**，而 `ReadAt` 明确拒绝更长的读。
**所以"一次读 1MiB"今天在实现上就被 scratch 尺寸挡住了** —— 这是本方案的前置改动之一（2.6 节）。

## 2. 方案：区域归位（region-homed layout）

### 2.1 地址映射

LBA 空间切成**区域**，每个区域 R 块（默认 **R = 128**，即 8MiB @64KiB 块）。
物理上给每个区域一个**固定的连续 home**：

```
lbaRegion(blk) = blk / R
i              = blk % R
slot(blk)      = phys(lbaRegion(blk)) * R + i          // phys: 区域的 home 序号
offset(blk,i)  = dataBase + (phys*R + i) * slotBytes
```

**这就是全部的核心**：同一区域内，块号差 1 ⇒ 物理偏移差 `slotBytes`。
不论它是被哪个 worker、什么顺序、什么时候写进去的。

文件布局（`slotBytes = BlockSize`，**不再含 stamp**）：

```
[0, 4096)                    superblock（不变）
[dataBase, dataBase+D)       数据区：regionHomes × R × slotBytes，纯数据，无洞
[stampBase, stampBase+S)     extent stamp 区：extentsTotal × 4096，集中存放
[idxBase, ...)               索引区：每区域一条记录
```

- `regionHomes = slotCount / R`（余数槽位丢弃；`slotCount` 由 `layout()` `l2.go:348-367` 同法算出）
- `E = blocksPerExtent`（默认 **16** ⇒ extent = 1MiB）；`extentsPerRegion = ceil(R/E)`；
  `extentsTotal = regionHomes * extentsPerRegion`
- 对齐：`4096 | BlockSize`、`4096 | R*BlockSize`、`4096 | E*BlockSize` ⇒
  `dataBase`/extent 起点/长度全是 4KiB 倍数，满足 `NO_BUFFERING`（`store_windows.go:15-19`）。

**把 stamp 从数据区搬出来是刻意的**：数据区因此完全连续、没有任何 4KiB 空隙，
"一个区域的 run"在磁盘上就是**一整块连续空间**，可以一次读走；stamp 集中后读/写/恢复也全是顺序的。

### 2.2 索引：区域目录 + 位图

| | 现状 | 方案 |
|---|---|---|
| RAM 主体 | `map[uint64]*slot`，**每块**一个 `slot`（`l2.go:181-198`）+ `slotsByNum []*slot` | `map[uint64]*region`，**每区域**一个：条数 ÷R |
| 存在性 | 每块 `valid uint32`（扇区掩码，`l2.go:184`） | 每区域 `bitmap []uint64`（1 位/块）+ 稀疏 `partial map[uint64]uint32`（仅"部分扇区失效"的块，绝大多数块不进这个表） |
| 落盘记录 | **20B/槽**，按**槽号**铺（`recordSize` `l2.go:86`、`pagesFor`/`indexOffset` `:369-377`） | **40B/区域**，按**区域号**铺 ⇒ 天然按 LBA 有序 |
| 落盘条数（10GiB / 64KiB 块） | 163840 条 × 20B = **3.1MiB** | 1280 区域 × 40B = **50KiB**（÷64） |
| 能回答的查询 | 只有单点（map） | 单点 + **范围**（"这段 LBA 里有哪几段是存在的、run 多长"） |

区域落盘记录：`lbaRegion(8) + version(8) + bitmap(R/8 = 16) + crc(4) + 保留(4) = 40B`。

**"能回答范围查询"是本方案的一半价值**：现状的 `map` 只能逐块问，
而合并读、预读、区域淘汰都要问"这一段里有什么"。

### 2.3 提交与崩溃一致性

沿用现有最重要的那条不变量（`l2.go:730-746`、`:800-806`）：

> **先写数据，后写描述数据的提交记录；提交记录带 generation + version + CRC。写序不可颠倒。**

改动是**提交单元从"块"变成"extent"（E 块 = 1MiB）**：

```
stampOffset(extentID) = stampBase + extentID*4096
stamp 内容 = { mag, lbaRegion, extentIndex, generation, version, bitmap(E 位), crc }
写序       = WriteAt(数据) → WriteAt(stamp)      // 顺序不可颠倒
```

- 数据撕裂 ⇒ stamp 还是旧的 ⇒ 校验失败 ⇒ **该 extent 的位在恢复时被清掉**，不会服务脏数据。
- **恢复只读 stamp 区，不读数据**：而 stamp 区是连续的 ⇒ 恢复过程本身是顺序读
  （现状是每槽 4KiB 散读 + 索引页按槽号铺）。
- generation 语义不变：`Drop()`（`l2.go:819-834`）换一个 generation，磁盘上所有旧记录自动作废。
- `stateOpen`/`stateClean` 两态标记、`unverified`/`dropped` 两个计数照搬，
  语义从"槽"变成"区域/extent"（`l2.go:470`、`:478-488`、`:862-902`）。

**必须写明的弱点（不要藏着）**：

| | 现状 | 方案 |
|---|---|---|
| 撕裂一次丢多少 | 1 块 = 64KiB | **1 个 extent = 1MiB** |
| stamp 开销 | 4096B / 64KiB = **6.25%** | 4096B / 1MiB = **0.39%** |

丢 1MiB 缓存数据（下次 miss 回后端再读）对读缓存是可接受的，
换来的是 stamp 开销降到 1/16 —— 两者可以按 `E` 调（`E=4` ⇒ 0.39%→1.56%，撕裂丢 256KiB）。

**版本升级**：`superBlockVer` 3 → 4。`:438-440` 已有现成的"版本不符就丢弃并重建"分支
⇒ **老缓存文件自动作废、重新建，不需要写任何迁移代码**。这是本设计风险最低的一环。

### 2.4 淘汰与替换

方案里**没有"块级淘汰"** —— 区域内是直映射（块 i 永远在区内第 i 个位置），
所以只有两种动作：**置位** 和 **整区域换出**。

- **分配**：维护空闲 home 表。首次填充按 home 顺序取 ⇒ **冷启动预热是纯顺序写**（数据区顺序 append）。
- **满后的 victim 选择**：区域级 CLOCK / S3-FIFO 变体（每个区域一个参考位 + 命中计数，
  与 L1 的 `newQ/midQ/oldQ` 思路一致，`cache.go:1472-1496`）。
- **整区域换出**：清 bitmap + `version++` + 写该区域**所有 extent 的 stamp**，
  **不写数据**。成本 = (R/E) × 4096B（8MiB 区域 = 8 个 stamp = 32KiB），
  比逐块环形回收更便宜，而且**不打断数据区的连续性**。
- **稳定态行为**（本方案与现状最大的差异）：
  热区域常驻之后，换入换出次数趋近于 0，**布局永久稳定**；
  而现状的环形 FIFO 是持续轮转的，**永远在破坏顺序** —— 这正是"缓存用久了就越来越慢"的来源。

### 2.5 容量、浪费与参数

**唯一的实质代价**：区域只热一部分块时，home 内空槽不能被别人用（直映射的固有代价）。

给一个量化口径：设热区域的**块填充率**为 f，则有效容量 ≈ `f × 标称容量`。旋钮：

| R | 区域大小 | 区域数（10GiB） | 目录大小 | 单区域浪费上限 | 跨区域冲突 |
|---|---|---|---|---|---|
| 64 | 4MiB | 2560 | 100KiB | 4MiB | 少 |
| **128** | **8MiB** | **1280** | **50KiB** | **8MiB** | **中（默认）** |
| 256 | 16MiB | 640 | 25KiB | 16MiB | 多 |

**关键判断**：按本文的前提（随机路径相对固定、且能被块覆盖），
热区域一旦被覆盖就会**持续被填满**（这正是它热的原因），所以填充率 f 应当接近 1，
浪费主要发生在"刚被换入、还没被访问完"的过渡区。

**因此这个参数必须实测，不能拍**：落地前先量 **区域填充率直方图**
（每个 home 的 `popcount(bitmap)/R`）。若直方图大量集中在低填充率，
说明 R 选大了或负载前提不成立 —— 此时退到 R=64，或改走 2.8 的紧凑模式。

> 注意本方案**不需要** `ScanEnabled` 那套顺序检测配合：
> 它不预测访问模式，只是让"已经在缓存里的东西，物理上就是相邻的"。
> 但 `ScanEnabled`/`ScanThreshold=32`（`cacheproxy.go:419-420`，写死 true）会把大顺序读**旁路掉**，
> 影响的是"哪些块能进缓存"，与布局无关 —— 见 §3。

### 2.6 读路径

**两个前置条件**（缺一个，合并读都做不成）：

1. **抬 `maxIO`**：`l2.go:303` 传的 `maxInt(slotSize, SuperBlockSize)` = 64KiB，改成
   `max(extentBytes, SuperBlockSize)`（默认 1MiB）。代价 = `storeShards` × 1MiB = **4MiB 内存**
   （`store_windows.go:31`、`:98`）。不改这一步，1MiB 的读会被 `store_windows.go:200-202` 直接拒绝。
2. **接口从单块改成区间**：`ReadSectors(blk, sec, n, dst)`（`l2.go:625`）→
   `ReadBlocks(blk0, nblk int, dst []byte) (hit int, err error)`。

**实现**：

```
一次 f.mu.RLock()                     // 替掉现状"每块一次"（l2.go:639）
按区域把 [blk0, blk0+nblk) 分组        // blk/R，同一组必然同一个 home
每组用 bitmap 求连续的 run             // 字扫描 + 末尾补零
每个 run 一次 store.ReadAt            // 长度 ≤ maxIO；更长就切段，但仍顺序
```

- **合并率是恒等式，不是概率**：同一区域的相邻块物理必然相邻 ⇒ 命中块只要在 LBA 上连续，
  读就一定连续。这是与所有"靠预测/靠排序"的方案的本质区别。
- 若 `dst` 的对应偏移是 4KiB 对齐的，可以直接读进 `dst`（省掉 `store_windows.go:213` 那次 bounce 拷贝）；
  否则保持现状的 bounce 路径，不引入新风险。
- **预读**：命中一个 run 时，顺带把同区域后面的 extent 读进 L2 暂存。
  物理相邻让这个预读**几乎零成本**（就是同一个大读）；窗口取 `min(剩余 run, maxIO)`，
  不要整区域拖进来。

**期望**：1MiB 命中读 **16 次 I/O → 1~2 次**，平均 I/O 大小 64KiB → 1MiB。

### 2.7 写/回填路径与失效

现状（每块独立）：`WriteSectors`（`l2.go:749-779`）全程持**全局写锁**，
里面一次 `WriteAt` 数据 + 一次 `WriteAt` 4KiB stamp ⇒ 1MiB 回填 = **16 + 16 = 32 次 I/O**，
外加 `optimize_261016.md` O8 记的"每回填一个 goroutine"。

方案：**按 `(lbaRegion, extentIndex)` 攒批**。

- 回填先落 extent 暂存；攒满 `E` 块**或超时**（建议 2ms）就写：
  `WriteAt(1MiB 数据)` → `WriteAt(4KiB stamp)` ⇒ 1MiB 回填 **2 次 I/O**。
- **超时必须有**，否则顺序流的尾巴会一直饿着不落盘。
- 顺带缓解 O8 的两个症状：I/O 次数 ÷16、全局写锁的持有次数 ÷16。
- 但**攒批与 `fence` 的交互必须重做**：`cache.go:1203-1205` 的注释说明
  "L2 序号与 epoch 校验在同一临界区分配"，攒批会把这个时序拉长，属于**必须同批设计**的项。

**失效**（`InvalidateSectors` `l2.go:782-812`，写回时由 `cache.go` 触发）：
区域版 = 清 bitmap 位 + 该 extent 的 stamp `version++` + 写 stamp；
"只失效了一部分扇区"的块进稀疏 `partial map[blk]uint32`（绝大多数块是全有全无）。
写序不变：**先 bump stamp 版本，再改索引页**（`:800-806` 的注释）。

**顺带解开 O7 的死结**：现在 L2 槽粒度 = L1 块粒度（`portal.go:198`、`target.go:538`
把 `cc.BlockSize` 直接传给 `l2.Open`），所以"块改小"会让 stamp 开销翻倍。
方案把 stamp 变成 extent 级后，这条耦合断了 ——
L1 用小块、L2 用大 extent 是可行的（需再加一层 `l2Blk = l1Blk / E` 的映射，**列后续项，不在本方案范围**）。

### 2.8 可选档：紧凑模式（rank）—— 把区域浪费清零

**只在 §2.5 实测出填充率偏低时才启用。**

- 区域内**只存存在的块**，按 LBA 顺序紧凑排列；区域记录加 `physBase` 与占用长度 `popcount`。
- 块 i 的物理位置由 **rank（前缀 popcount）** 算出：
  `offset(blk) = dataBase + physBase*slotBytes + rank(bitmap, i)*slotBytes`
  rank 用 64 位字 + 查表，O(1)。
- 收益：**零浪费**，"存在的连续 run"仍是磁盘上连续的一段（更紧）。
- 代价：区域内容会变 ⇒ 新增块时若后续空间被占，需要**区域内压缩（memmove）**或搬迁。
  复杂度显著上升。
- **建议：先不做。** Phase 1~3 拿到填充率数据后再定。

| 项 | 变更 |
|---|---|
| `Config`（`l2.go:136-147`） | 新增 `RegionBlocks`（默认 128）、`ExtentBlocks`（默认 16）、`MaxIOBytes`（默认 1MiB） |
| `superBlockVer`（`l2.go:57`） | 3 → 4；`sbOff*` 表（`:93-103`）新增 `regionBlocks`/`extentBlocks`/`regionHomes`，插在 `sbOffCRC` 之前（superblock 有 4096B，位置充裕） |

### 3.3 与 `ScanEnabled` / `ScanThreshold`

`cacheproxy.go:419-420` 把顺序扫描准入写死为 `true` / 32 阈值，它决定的是
**"哪些块允许进缓存"**（大顺序读被旁路，防止冲掉热点）。
本方案管的是**"进了缓存之后怎么放"**。两者不冲突，但有一个前提要知道：

> 若实测发现热集是"稀疏的少数块"（区域填充率低），说明"能被块覆盖"这个前提偏弱，
> 应当退到 §2.5 调小 R，或启用 §2.8 的紧凑模式 —— **而不是去改扫描策略**。

| Phase 2 | **已完成** | 区域归位（块 → `home*R + blk%R`）；`regionBlocks` 配置 + 落盘 + 尺寸不符即丢弃；把手（hand）淘汰；目录由槽反推（不落盘） | §2.2 的**落盘索引**仍是每槽 20B 记录（`map[uint64]*slot`），不是每区域 40B；`Slots/UsedSlots` 语义未重述 |
| Phase 2（§2.4 victim） | **已完成** | 淘汰改为 **CLOCK**：每个 home 一个参考位（`homeRef []atomic.Bool`），命中读置位、把手扫过时清除，空 home 仍优先；`Evictions()` 暴露换出计数 | 没做"命中计数"——参考位已给足第二次机会，计数会引入"刚换入=0"的假冷 |
| Phase 3 | **未开始** | — | 见下（有阻塞项） |

**§2.4 那处判断要修正一行**：方案原文写"读只持读锁，所以没有参考位可置"
（对应 `evictHomeLocked` 的旧注释）。这条**不成立**：参考位是原子量，命中读在
`RLock` 下 `Store(true)` 即可，而淘汰扫在 `WriteLock` 下 —— 两者由 RWMutex 天然互斥，
所以一次扫掠期间不可能有读来置位，扫掠必然终止。**代价为零**，收益是
"被读的区域不再因为轮到号而被换出"，这正是 §5.1 里"换入换出趋近 0"的稳态。

**Phase 3 有一个必须先解决的正确性缺口**（不要照抄 §2.3 直接动手）：
extent stamp 与区域记录都是**整块粒度**的位（`E` 位 / `R` 位），
而失效路径 `InvalidateSectors(blk, sec, n)` 会产生"只失效了一部分扇区"的块。
§2.3 把这种块放进内存里的稀疏 `partial map[blk]uint32` —— 但它**不落盘**：
崩溃重启后，区域记录只会说"这个块在"，于是**按全有效恢复，把已失效的扇区当命中服务出去**。
这是数据正确性问题，不是性能问题。可选的收口方式（择一，需先定）：
1. 落盘时把带 partial 的块的位**清零** ⇒ 重启后该块 miss（安全，丢一个块）；
2. extent stamp 里额外存该 extent 内 partial 块的位置（`E=16` 时 16 位足够），
   但会引入第二套元数据；
3. 干脆让 `InvalidateSectors` 的块级失效**退化为整块丢弃**（不产生 partial），
   代价是失效后同一块的其他扇区也 miss。

同理，§2.7 的回填攒批与 `cache.go:1203-1205` 的 `fence`/epoch 时序**必须同批设计**，
这一条在 Phase 3 动之前就要定下来，否则攒批会把"L2 序号与 epoch 在同一临界区分配"
这个前提拉长。

## 5. 验收口径与测试

### 5.1 指标

| 指标 | 目标 |
|---|---|
| **顺序率** = 1 - 合并后 I/O 次数 / 合并前 I/O 次数 | 稳态 ≥ 90% |
| **平均 I/O 大小** | 64KiB → **1MiB** |
| **1MiB 命中读的 `ReadAt` 次数** | **16 → 1~2**（硬指标） |
| **区域填充率直方图** | 决定 R 与是否上 §2.8 |
| **区域换入换出次数 / 秒** | 稳态趋近 **0** |
| L2 读延迟 P50 / P99、`ReadAt` 总次数 | 不劣化 |

### 5.2 测试（在现有测试结构上扩展）

- **邻接性断言**：`slot(blk+1) - slot(blk) == 1` 当且仅当同区域 ——
  这是本方案的**核心不变量**，必须有测试钉住，防止后人改回环形分配；
- **区域淘汰**：换出后旧区域的块全部变 miss，且绝不服务脏数据；
- **撕裂（对应现有 stamp/verify 测试）**：只写 extent 数据、不写 stamp ⇒ 恢复后该 extent 全部 miss；
- **版本升级**：打开 v3 文件不报错、内容被丢弃（走 `l2.go:438-440` 现成分支）；
- **攒批饿死**：不足一个 extent 的回填，超时后必须落盘；
- **对齐**：`dataBase`、extent 起止、stamp 起点全是 4KiB 倍数
  （`NO_BUFFERING` 硬要求，参照 `store_windows_test.go` 的现有对齐测试）；
- **内存 Store 路径**（`l2.go:1054`）跑全部新测试，保证与平台无关。

### 5.3 白盒计数断言（防回归）

参照内存治理 M1 那个"反向验证"的测试风格：埋原子计数，
断言"1MiB 命中读 = 1~2 次 `store.ReadAt`"这个**新上界**，
并在 Phase 1 时先断言它的旧上界（16 次）——落地后收紧。谁把逐块调用加回来，测试就会红。

## 6. 风险与不做

| 风险 | 说明 | 缓解 |
|---|---|---|
| **负载前提不成立** | 热集稀疏 ⇒ 区域填充率低 ⇒ 有效容量被浪费吃掉 | **Phase 0 先量**；退 R=64 或上 §2.8 |
| 撕裂颗粒变粗 | 崩溃后从丢 64KiB 变成丢 1MiB | 读缓存可接受；`E` 可调（E=4 ⇒ 丢 256KiB） |
| 攒批改变 `fence`/epoch 时序 | **正确性相关** | 与 O8 同批设计；`invalidate_test.go` + `-race` |
| 老缓存文件全部作废 | 升级后首次冷启动 | 一次性；就是 `:438-440` 的现成路径 |
| 大 `maxIO` 常驻内存 | 4 shard × 1MiB = 4MiB | 可忽略；`newAlignedBuf` 上限 1GiB（`store_windows.go:69-71`） |
| 对外方法语义变化 | `Slots/UsedSlots` 等被 `agent` 侧读取 | 落地前逐一核对调用方 |

**本文档不做**：不动 L1 索引（261017 的范围）、不动数据面（261016 的 O4/O5）、
不实现 §2.8 紧凑模式、不核对对外方法的全部调用方。
